<h2>按「需要什么身份」来分场景</h2>
<p>住宅 IP 不是所有业务的通用解。它的核心价值是提供「看起来来自普通家庭用户」的网络身份。凡是需要这个身份的环节，它有价值；不需要的环节，用它就是浪费。</p>

<p>强度越高的场景，越应该用稳定独享的住宅出口；强度越低的场景，用机房或动态资源更划算。</p>

<h2>强度高的场景要注意什么</h2>
<p>这类场景的共同特点是一旦出问题，损失不可逆。所以配置上要额外注意三点：出口独享、配置稳定、变更谨慎。</p>
<p>出口独享保证没有他人行为干扰。配置稳定意味着长期不换参数、不换设备。变更是最大的风险源，非必要不动。</p>

<h3>账号注册环节的特殊性</h3>
<p>注册是平台观察一个新身份最密集的时刻。此时的网络环境、设备环境、行为节奏都会被记录。用一条被滥用过的地址注册，等于一开始就带着负面记录。所以注册环节对地址洁净度的要求，高于日常登录。</p>
<h3>广告与投放环节的特殊性</h3>
<p>这个环节需要的不是「隐藏身份」，而是「看到真实结果」。用本地地址查看自己的广告呈现，才能判断素材、落地页、价格在目标市场是否正常。这时的关键不是独享，而是地区准确。</p>

<h2>强度中等的场景怎么做</h2>
<p>中等强度场景通常允许一定的变动，但仍需保证地区正确。做法是用按需分配的住宅资源，不追求长期固定，按任务周期使用。</p>
<p>这类场景成本敏感度高，用固定独享资源会显著拉高单次任务成本。按任务采购、用完即停，是更合适的模式。</p>

<h2>强度低的场景别用住宅</h2>
<p>公开信息采集、大文件传输、系统更新，这些环节用住宅资源是纯浪费。住宅带宽有限、按条计价，成本高且效率低。</p>
<p>正确做法是这类流量走机房链路，只把必须由住宅身份发起的请求分流出去。分流做在网关层，规则只维护一份。</p>

<h2>组合使用的实际架构</h2>
<p>成熟的做法是三层：住宅出口负责身份相关操作，机房出口负责重流量任务，本地直连负责无需出海的访问。三层在网关层按规则分流。</p>
<p>这样配的好处是成本与风险同时可控：住宅出口只承载必须的部分，带宽压力小；机房出口承担重活，性价比高；本地直连保证日常效率。</p>

<h3>分流规则要能查</h3>
<p>规则多了必须能查「某个请求走了哪条出口」。没有这个能力，出问题只能猜。建议在网关保留日志，至少记录出口选择结果。</p>
<h3>不要在同一账号上混用出口</h3>
<p>分层是给不同任务用的，不是给同一账号用的。同一账号在同一时段从多个出口登录，是明显的异常信号。</p>

<h2>常见问答</h2>
<h3>只做浏览需要住宅 IP 吗</h3>
<p>取决于浏览对象。公开页面不需要；需要登录才能看的内容，身份就有意义。先判断是否涉及登录状态。</p>
<h3>采集一定要住宅吗</h3>
<p>不一定。多数公开数据用机房或动态资源即可。只有在被严格限流时才需要考虑住宅，且应控制请求密度。</p>
<h3>一个业务能用混合资源吗</h3>
<p>可以，按环节分。但要保证同一账号的核心操作始终在同一个出口上，不要在不同类型之间来回切。</p>
<h3>怎么判断自己的场景强度</h3>
<p>问三个问题：是否涉及登录、出问题的损失有多大、平台是否校验地址类型。三个都偏重的，属于强场景。</p>
